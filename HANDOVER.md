## Architecture in one paragraph
Every project is one JSON document (projects.data). Events, library (people, locations, general tasks), finance (admin-only) and members are their own tables. src/lib/store.jsx holds the whole state, persists to localStorage in local mode or syncs diffs to Supabase (debounced upserts, realtime merges). Pages call `update(fn)` / `updateProject(id, fn)` and mutate a draft. Permissions: per user, per module, view/edit, plus project access; RLS enforces membership, project access and edit rights.

Two ordering traps, both noted inside the files themselves:
- **share_access.sql** goes after shares.sql, and again whenever shares.sql is re-run, because that file recreates the older wide-open shares_members policy. It now decides per kind: call sheets open to every member, estimates `is_admin()`, everything else the Share permission.
- **estimates.sql** goes after deliveries.sql, because that file recreates the delivery-only share_respond.
- **share_pin.sql** goes after shares.sql and share_track.sql, because both recreate the one-argument share_get that has no code check.
- **notices_ack.sql** goes after notices.sql, because that file recreates the wider update rule.
- `supabase/chat_likes.sql` (8 Oct): hearts on chat messages, a `likes` column and the `chat_like` function.

### Calendar feeds: read-only .ics calendars on the Calendar page (7 Oct)

### Google Calendar, connected both ways (29 Sep) — needs setup, not yet tested live
Alex: "Μπορούμε να συνδέσουμε ένα συγκεκριμένο ημερολόγιο της Google;" Asked which of two shapes he wanted (a one-way subscribe link, simple, no Google credentials needed, vs full two-way sync, bigger, needs Alex to create a Google Cloud OAuth app) — he picked **full two-way sync**.

**What it does**: one specific Google Calendar connects to the whole workspace. Events made on the Calendar page (shoot days, prep, scouts, everything except days off, which stay internal) get pushed there on save and removed there on delete. Events made straight in that Google Calendar come back here on a pull, as their own kind — "From Google Calendar" in the type list and legend — editable like anything else; editing one here pushes the edit back. A pull happens when the Calendar page (the workspace-wide one, not a project's own tab) is opened, and on the new **Sync now** button next to Export .ics. There is no live push from Google (that needs a verified public domain and a webhook endpoint, well past what this setup can support), so a change made directly in Google Calendar shows up here on the next sync, not instantly.

**Why two-way turned out buildable with no new backend**: the existing `events` table already stores each event as flexible JSON (`data jsonb`), and workspace settings are the same (`workspaces.settings jsonb`) — so a `googleEventId` on an event and a `googleCalendarId`/`googleClientId` in settings needed no SQL migration at all, no new file in `supabase/*.sql`. The whole thing is one new Edge Function (`supabase/functions/google-calendar/index.ts`) plus a client module (`src/lib/googleCalendar.js`) and the usual Settings panel, following the pCloud integration's exact shape: the long-lived credential (here, a Google **refresh token**) is a function secret, never written to the database, pasted in by hand once.

**Why it needed a code exchange, unlike pCloud**: pCloud hands back a usable token directly in the redirect (`response_type=token`), good forever. Google only does that for an access token that expires in an hour; a lasting connection needs the authorization-code flow, which needs a client secret to exchange the code — so that one exchange (`action: "connect"` in the function) happens server-side, the only step pCloud's flow didn't need. Everything after that (minting a fresh access token from the refresh token, listing calendars, reading/writing/deleting events) is the function talking to Google directly with that one secret, same as pCloud's token.

**Setup, written on the Settings panel itself** (Settings → Integrations → Google Calendar, administrators only, needs the online database): a Google Cloud project with the Calendar API enabled, an OAuth Client ID (Web application, the exact redirect URI is shown on the panel), your own account added as a Test user on the OAuth consent screen (Google will warn "unverified app" when connecting — expected, click through it), `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` as Edge Function secrets, the function deployed (name `google-calendar`), Connect (allow access, come back with a refresh token shown once, copy it in as `GOOGLE_REFRESH_TOKEN`), Test connection, pick the calendar.

**Not yet tested against the real Google API**: this sandbox has no Google Cloud credentials to connect with and the build itself can't run here either (registry.npmjs.org blocked, see the earlier PDF-colours entry) — the token exchange, calendar listing, and event push/pull/delete logic in the Edge Function are written to Google's documented Calendar API v3 and OAuth2 endpoints, re-read for correctness, but have not been exercised against the live API. Please go through the setup steps above and try Connect → Test connection → add or edit an event → Sync now, and tell me exactly what happens (or what error shows) if something doesn't work — that is the fastest way to find a real bug versus a documentation gap.

**Known limits, by design, not oversights**: only one calendar at a time, shared by the whole workspace (same model as the one shared pCloud account) rather than a separate connection per person. Days off never sync (an administrator's internal scheduling, not something to put on a shared calendar). Events already on the calendar before connecting are not bulk-exported; only ones added, or opened and saved, afterwards start syncing — reopening and saving an old event once is enough to bring it in. A conflict (both sides changed the same event between syncs) is not specially detected; the next pull simply overwrites the local copy with Google's version.

### Two traps worth not rediscovering
- **`memberToUser()` used to fill missing permission keys with `view`.** A member's stored row only carries the modules that existed when they were last saved, so every module added later was handed to the whole team the day it shipped. That is how Drives and Share reached people who were never given them. It fills with `none` now. If someone says a page disappeared, that is why: give it to them in Team.
- **Postgres writes a timestamp as `...+00:00`, the browser writes `...Z`.** Compared as text they are never equal and `Z` sorts above `+`, so the same instant compares differently depending on who wrote it. Everything asking "is this newer" goes through `whenMs()` in store.jsx.

### Easy to forget, still true
- **Supabase Auth has Confirm email OFF.** A new person registers, then Alex adds them in Team with **the exact email they registered with**, then they reopen the app.
- **A member writes only their own `profile` column**, through `set_my_profile()`. The members row also holds role, permissions and project access, which is why there is no plain "update your own row" policy: that would let anyone make themselves an administrator.
- Profile photos and the company logo are **data URLs inside the row**, resized in the browser. No storage bucket is involved in either.
- `canSeeProfileDetails()` in Profile.jsx is the single rule for who sees a phone and a birthday (the member chooses: whole team, or administrators only). Name, photo, position and bio are always visible to the team.
